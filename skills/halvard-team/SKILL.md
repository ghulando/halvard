name: halvard-team
description: Coordinate a multi-agent team through Herdr only when the user explicitly asks to run one. Requires HERDR_ENV=1; ordinary implementation requests do not trigger this skill.
---

Before doing anything, read `printenv HERDR_ENV` and confirm its output is exactly `1`. If the executed check reports another value or an unset variable, say you are outside Herdr and stop. A workflow denial is not a failed environment check: report the blocked prerequisite to the user. Read the herdr skill, then `herdr --help` and `herdr agent` for installed syntax. Repository instructions and workflow guards still apply; never work around a denial.

The guard needs reviewed personal `readCommands` for `["printenv", "HERDR_ENV"]`, Herdr help and read-only agent list/get/read/wait commands; use typed rules for their options as described in docs/configuration.md. Do not classify prompt/send-keys or other controls as readers. Controls run freely on a feature/fix branch but cannot run on protected branches or in plan/review mode: start the task branch and exit that mode first. The lead's own command approvals always go to the user, including approvals needed to relay a worker's request.

## Team setup

The repository's `.halvard.json` holds the team. Run `node <plugin-root>/bin/halvard.ts team show` first.

When `team` is `null`, ask the user these questions before anything else. Use the harness's question tool when it has one. The choices for each role are `pi`, `claude`, `codex`, `grok` and `cursor`.

1. Lead: which harness coordinates, writes briefs, watches the panes and records the review? The lead writes no product code.
2. Dev: which harness implements and runs the gate? It must differ from the lead.
3. Reviewer: which harness reviews the dev's diff in its own pane? It must differ from the dev.
4. Investigator: which harness, if any, reads risky code before the brief? The user can answer none.
5. Watch: does the lead read the other panes and report progress, stalls and errors to the user?
6. Nudge: may the lead send a short prompt to an idle or stuck worker?
7. Approve: may the lead answer a worker's permission prompt for reads, edits inside the repository or task workspace and the gate (`reads-edits-gate`), or does every prompt go to the user (`none`)?

Save the answers with `node <plugin-root>/bin/halvard.ts team set --lead <harness> --dev <harness> --reviewer <harness> --investigator <harness>|none --watch on|off --nudge on|off --approve reads-edits-gate|none`. The command changes the workflow configuration, so it asks the user once more. It cannot run on a protected branch: create the task branch first.

When a team is saved, show it to the user and ask: keep this team, or change it? For a change, ask only the questions the user wants to change, then run `team set` with only those options.

The current session must be the saved lead. If it is not, tell the user to start this skill in the lead's pane, and stop.

## Preflight

Before briefing anyone, check every prerequisite and report all missing ones to the user in one message instead of failing on them one by one. The tree is clean or the user has said how to place existing changes, and the task branch exists. Personal `readCommands` hold the rules above. Claude's `permissions.additionalDirectories` and Codex's `writable_roots` under `[sandbox_workspace_write]` include the workspace root (`~/.halvard/workspace` unless `HALVARD_WORKSPACE` is set, never all of `~/.halvard`), and a Grok or Cursor sandbox, when on, allows writes there; otherwise every report write asks. When the gate runs npm, every sandbox that gate runs use also allows writing the npm cache (`npm config get cache`): Codex's `writable_roots`, and Claude's sandbox write paths when its sandbox is enabled. Otherwise every gate run asks for escalation. Read config files to check; never edit the user's harness configuration without their yes.

Before the first brief, the lead confirms pane-text detection works with `herdr agent read <name> --source visible`. Plan the handoff: the author finishes notes and reports, runs the full gate as its last action with no later command or edit, and reports its session key; the lead records the pane review with that key. Create task files through `task-start` with `--team`. It records the saved team where agents cannot edit it, and from then on the guard denies file edits by the lead, reviewer and investigator harnesses: only the dev changes repository files, and the lead edits only task notes. Shell commands are not checked, so briefs still keep each role to its own work; a follow-up on the same branch copies the branch and full base SHA, sets its own author and a fresh `reviewCycle`, and creates its task workspace with mode 0700. A follow-up stays on the branch the user is already working on: never brief a worker to run `task-start` for it. Before sending acceptance criteria, grep the whole test tree, not only the tests an investigation named, for every behavior a criterion changes: identifiers, error strings, SQL and fixture names. List every test that asserts the old behavior in the brief. Each conflict is a scope question for the user before implementation starts, not work for the implementer; ask them together in one message.

## Start and coordinate

Roles come from the saved team: the lead and architect, the dev, the reviewer and, when set, the investigator before the brief for risky code. Recorded review is the only review. One harness may hold several roles that the team allows, for example lead and investigator, but the dev never reviews its own work. Describe responsibilities by role, not harness.

List agents with `herdr agent list`, then name them with `herdr agent rename <pane> <role-name>`. Use the role names (`lead`, `dev`, `reviewer`, `investigator`) unless the user chooses others. Discover pane IDs from live output. If an agent is missing, follow the herdr skill to create a sibling pane and start it; preserve the working directory and user focus.

Messages follow hub and spoke: workers report to the lead, which relays briefs, evidence and findings. Assign one task per agent. Before prompting, check `herdr agent get <name>`; never prompt a working agent. A worker waiting at an approval dialog can still report `working`, so answer it as the approval paragraph describes. Use `herdr agent wait <name> --timeout 60000` and confirm it is idle or done. Unknown state is not readiness. Send long work with `herdr agent prompt <name> "<brief>"` without `--wait`, or add `--wait --timeout <ms>` sized to the work. Poll status with `herdr agent get <name>` and pane text with `herdr agent read <name> --source visible` while work runs. Treat any change out of `working` as a report to read, including `idle`: Codex can finish without passing through `done`. While a worker or background subagent runs and `monitor.watch` is on, report its progress to the user every 10 minutes from its latest file writes or test runs, and say it has stalled when nothing changed since the last report, or when its pane shows an error. With `monitor.nudge` on, the lead may send an idle worker that stopped without a report one short prompt: ask for its report path, or tell it to continue its brief. Never nudge a working agent or one at an open dialog. With nudge off, report the stall to the user instead. Read completed results with `herdr agent read <name> --source recent-unwrapped --lines 200`. A timeout or stalled prompt does not prove loss; read the pane before resending.

Team files live in the task workspace that `task-start` and `task-resume` print, `~/.halvard/workspace/<repo>/<task-id>/`, never in a harness scratch directory. Each file has one writer, named by its harness prefix. With Claude as lead, Codex as dev and Pi as investigator, the lead writes `claude-brief-codex.md`, the dev writes `codex-report.md` and the investigator writes `pi-findings-1.md`. Every agent may read every file; the guard denies file-tool writes to another writer's files. Send a short prompt that names the brief path, and ask workers to reply with only the path of their report.

Every brief carries the command rules below, known budgets and invariants the change can hit, including size limits enforced by tests, and this rule: if an existing test fails, stop and report; never edit, skip or weaken it. Briefs to the investigator and the reviewer give only commands the guard classifies as reads; anything else, including running tests, belongs to the dev or lead. Anything the guard cannot classify stops for approval, and Pi has no native permission layer. Prefer native read, ls, grep and find tools. In shell, use plain read commands with literal paths: no loops, `$` variables or substitutions, no globs in a chain that also runs `echo` or another non-reader. Comments go on their own line, never after a command, and contain no quotes, backslashes or shell operators.

## Task and review

The lead owns scope, architecture and acceptance criteria, and sizes the process to the change. Every factual premise a decision rests on cites a file:line the lead read itself; a claim from an investigation is a lead to check, not a fact. Keep preparation proportionate while a worker waits: check the prerequisites above, read what the brief's decisions rest on, and send the brief; investigate further only for a question the brief cannot leave to the dev. Report an edit, including to a brief or task notes, as made only after reading the changed lines back. The dev's final gate is the full check; the lead runs targeted checks for its own decisions and does not run the full suite before that gate. Every brief has a Done-when clause for each acceptance criterion. Write briefs and review contracts in [halvard-write](../halvard-write/SKILL.md) Strict mode, and ask the reviewer to write its findings the same way. Docs, skill and wording changes get one implementer pass and one recorded review; the lead accepts the nits. Investigate risky code before the brief, without an informal review pass. Present simple and thorough design choices to the user with their implementation and review costs, recommending the simple one unless risk justifies more. A small-sounding requirement, such as handling files a running process still writes, can dominate the work.

When the change reads, writes or deletes real user data or the live environment, the lead runs its read-only or dry-run path against the real environment before the first recorded review and checks the result against the acceptance criteria. Fixtures show the code does what the brief says; only the real environment shows whether the brief was right.

The investigator reads relevant code, tests and risks without editing. The implementer follows the brief, starts or resumes the feature/fix branch through workflow, preserves dirty work, keeps task notes current, runs the full gate and reports evidence to the lead.

The recorded reviewer assesses acceptance criteria and boundary/adversarial cases, reporting actionable findings with severity, file:line, failure and suggested fix. A passing first review supplies the completion receipt; round 2 is needed only after a blocked round 1 and fixes. For every change, after a blocked review there is at most one fix pass; anything still open goes to the user. The lead validates findings and batches confirmed fixes; never run a separate fix-and-gate cycle per nit.

In a team, review happens in a visible pane, never in a headless reviewer process. The reviewer is the saved team reviewer, never the author. The lead briefs it in `<lead>-brief-<reviewer>-review.md` with the task file, the acceptance criteria and this contract: read the diff and the code, edit nothing, and write `<reviewer>-verdict-round<N>.json` in the task workspace holding only `{"verdict":"pass" or "blocked","standards":"invariant walk","spec":"acceptance evidence","findings":[{"severity":"blocking" or "should-fix" or "nit","location":"file:line","problem":"...","suggestion":"..."}]}`. The workspace writer rule lets only that harness write the file. A pane reviewer gets no runner prompt, so a round 2 brief also carries the preceding round's findings from `<its reviewer>-review-round<N>.md`, where `review-status <task-file>` names that round's reviewer, the re-review rules, and any `reviewDeferrals` the user recorded for the task. The reviewer reports a deferred finding that still applies with `"deferral": "<finding id>"` and its recorded severity, location and problem unchanged. The reviewer states for each earlier finding whether the tree resolves it, and an unresolved earlier finding keeps its severity. A new issue stays blocking only when it would block a first review, and other new issues are nits starting "Follow-up:". The lead then records it with `node <plugin-root>/bin/halvard.ts review <task-file> --author <author> --reviewer <reviewer> --round 1|2 --gate-session <key> --pane`, retaining the author and using its session key. The command checks independence, the author's current gate receipt and an unchanged tree, then writes the receipt and `<reviewer>-review-round<N>.md`; a reviewer edit changes the tree and voids it. The lead's unclassified commands clear only the lead's own gate receipt. The record command may need the user's approval in the lead's session. Follow halvard-review for fixes, re-review, current gate receipts and completion.

## Approval and shipping

The lead approves teammates' requests by default, inside the saved `monitor.approve` scope. With `reads-edits-gate`, the lead itself answers only a file read, an edit to a file inside the repository or the task workspace, and the gate command from the worker's session context. Network access, installs, deletes outside the repository, commands it cannot classify, edits to workflow configuration, and every commit, merge, push or publish go to the user with the exact operation. With `none`, every request goes to the user. A worker hitting `approve halvard <id>` or an approval dialog stops and reports the exact operation to the lead. The lead checks that it is inside the current brief and the scope, and approves it. A Cursor worker's denial names a `halvard approve` command for the user's own terminal; the guard denies it to every agent, so relay it to the user. Send `herdr agent prompt <name> "approve halvard <id>"` only to a worker that has stopped and is idle, without an open dialog. Herdr rejects `agent prompt` for a blocked worker with `agent_blocked`; answer the displayed dialog with send-keys instead. Out-of-scope operations and the lead's own requests always go to the user. No agent approves its own request.

The lead need not wait for a report or a `blocked` status. Pi stays `working` while its approval dialog is open, so detect dialogs from pane text with `herdr agent read <name> --source visible`, which works while an agent is working; `--lines N` fails with `agent_not_idle` then. Count a dialog as open only when its question is at the bottom of the visible pane; the same text higher up is scrollback from an earlier question. Read the full operation and displayed choices. For an in-scope dialog, including Pi's workflow request, select the one-time yes with `herdr agent send-keys <name> <key>`. Never select a persistent "don't ask again" choice, guess keys or send ordinary prompts into an open dialog. To type a free-text answer to a Codex question, send one key per `send-keys` call, `space` for each space, then `Enter`; read the visible pane and send `Enter` again if the answer is still in the input box. A Codex worker blocked by Halvard calls `halvard_request_approval`, and Codex shows a form headed `Halvard approval request` with the repository, branch, operation and expiry, and the choices Approve once and Reject. Treat it like any other dialog under the approval rules above: the lead selects Approve once only for an operation inside the `monitor.approve` scope, and every commit, merge, push or publish goes to the user. The tool can also return text that names `approve halvard <id>` when Codex cannot show the form; handle that like a text request.

After done and before asking to commit, the lead offers [halvard-retro](../halvard-retro/SKILL.md) and, on the user's yes, runs it in its own pane over the team's events. Retro reads Claude, Codex and Pi transcripts; Grok and Cursor take part through their team files. Only the lead commits or merges, after the user's explicit yes. The lead stages code and tests by name, never `git add -A`, `git add .` or `git commit -a`, and asks separately before including the task files under the configured `taskDirectory` or the `.halvard.json` changes, naming any change to `reviewExceptions` or `reviewDeferrals`. On the protected base branch the guard accepts only plain shipping commands, each needing approval: `git merge --ff-only <branch>` and then `git branch -d <branch>...` for one or more merged branches, each run alone from the repository root without `git -C`, a pipe or a chain. Push and publish require a separate explicit yes.
